# 추천 점수 산식 설계 (B 파트: 점수 산식 + 시뮬레이션)

> 상태: **임시안 v2 (`provisional-v2`)**, 2026-11-21. 중심 0.8 가중은 팀 초안대로 유지(2026-11-21 결정). 가짜 데이터 시뮬레이션으로 정했고, 실제 데이터로 다시 돌려 확정한다.
> 근거 피드백: 중간발표(2026-11-11) — 점수화 보완, 시나리오 시뮬레이션, 인접 8셀 가중치 차등, TOP 5 추천 이유 설명.
> 관련 요구사항: Notion PRD B3(점수)·B4(최소 인구)·B5(정렬)·N15(설정 분리)·N16(기준선)·N17(민감도), 결정 기록 D14·Q7.
> 팀 초안(정동민, 2026-11-11): 100점 = 전체 인구 40 / 타깃 비율 40 / 유동유형 20, 인구 = 중심 셀 × 0.8 + 주변 셀 × 0.2.

## 1. 한눈에 보기

| 단계 | 내용 | 코드 |
|---|---|---|
| ① 조건 → Cell 값 | Cell마다 N(전체 유동), T(타깃 유동), Tf(타깃의 선택 유형 값) 합계 | `RecommendationScorer.sql()` |
| ② Cell → 게시대 | 중심 0.8 + 주변 0.2(거리 가우스 차등), 없는 칸 제외 후 합 1 → 일평균(명/일) | `CellWeights`, `RecommendationScorer.inputs()` |
| ③ 게시대 → 점수 | (최소 타깃 인구 미만 제외 후) A 유동 규모 40 + B 타깃 비율 40 + C 유형 비중 20 | `ScoreFormula` |
| ④ 정렬 | 점수↓ → 게시면수↓ → 부착금액↑(없음 뒤) → 게시대 ID↑ (명세 4.6) | `ScoreFormula.ORDER` |

- Java(서비스): `backend/src/main/java/com/capstone/backend/recommendation/`
- Python(참고 구현·시뮬레이션): `python/src/data_processing/scoring.py`, `simulate.py` — 같은 규칙. 가짜 데이터 시나리오 2개에서 두 구현의 순위가 전부(59개·290개) 일치함을 확인했다.

## 2. 지표 정의

조건 적용은 조회 API(`PopulationFilter`)와 같은 UNKNOWN 규칙을 따른다. 성별 ALL이면 UNKNOWN 포함, 연령·시간대는 전체 선택일 때만 포함, 요일 ALL이면 포함.

| 기호 | 정의 | 적용 조건 |
|---|---|---|
| N | 체류+보행+주행 | 기간·요일·시간대 (성별·연령 전체) |
| T | 체류+보행+주행 | N + 성별·연령 |
| Tf | 선택 유형 값(보행이면 walk) | T와 같은 행 |

| 지표 | 원값 | 배점 | 0~1로 바꾸는 방법 |
|---|---|---|---|
| A 유동 규모 | N | 40 | log(N)을 후보 안 최소~최대로 0~1 (가장 큰 게시대 = 1, 범위는 최소 10배) |
| B 타깃 비율 | T/N | 40 | 후보 전체 비율(ΣT/ΣN) 대비 배수(리프트)를 log 척도로: **같으면 0.5, 2배 이상 1, 절반 이하 0** |
| C 유형 비중 | Tf/T | 20 | B와 같은 방식 (기준 ΣTf/ΣT) |

- **규모 최소 범위(10배):** 후보가 적고 유동이 비슷하면(예: 20 vs 18.8명/일) 최소~최대가 그 작은 차이를 40점 대 0점으로 벌린다. 그래서 log 척도는 최소 10배 범위로 잡는다. 후보끼리 10배 넘게 차이 나는 보통의 경우에는 영향이 없다(가짜 데이터 시나리오 결과 동일). DB 통합 테스트를 만들다 발견했다.
- 유동 유형 `ALL`이면 C가 모두 1이라 의미가 없으므로 빼고 A·B를 **50·50**으로 키운다.
- N이 0인 게시대, 3×3 모든 칸에 조건 데이터가 없는 게시대는 결과에서 뺀다(명세 1.2).
- log로 더하므로 A+B ≈ log(N) + log(T/N) = log(T). 초안 구조(전체 인구 + 비율)를 그대로 두어도 **타깃 규모가 반영된다**.
- **비율 보정(shrink 0.5):** 인구가 적은 게시대의 비율은 표본이 작아 크게 튄다. 점수에 쓰는 비율은 후보 평균 쪽으로 당긴다:
  `B' = (T + k·ΣT/ΣN) / (N + k)`, `k = 0.5 × 후보 N 중앙값` (C는 `Tf/T`에 같은 방식, 중앙값은 T). 중앙값 규모 게시대는 평균과의 차이를 2/3만, 아주 큰 게시대는 거의 그대로 반영한다. 화면에 보여주는 비율(`rawValue`)은 보정 전 값이고, `lift`(평균의 몇 배)는 보정 후 값이다. 근거는 4장 E8.

## 3. 인접 8셀 가중치 차등

```
w(중심) = 0.8
w(주변 i) = 0.2 × k(dᵢ) / Σk(d)      k(d) = exp(-d² / 2σ²),  σ = 250m (한 칸)
d = 게시대 위경도 → Cell 중심 거리 (board_cell.distance_meters)
데이터가 없는 칸은 빼고 남은 칸의 w 합이 1이 되게 다시 나눈다.
```

- 게시대가 중심 Cell 안 어디에 있느냐에 따라 주변 칸 비중이 달라진다. 예: 중심에서 136m 떨어진 게시대는 가까운 이웃(178m) 0.042, 반대쪽 대각선(490m) 0.008.
- 같은 중심 Cell을 쓰는 게시대도 위치가 다르면 점수가 구분된다(시나리오 2: 공유 묶음 67개 중 22개 구분, 나머지는 **좌표 자체가 같은** 게시대 → 명세 4.6 동점 정렬로 순서 결정).
- 결과는 '가중 평균 Cell 값'이라 상세 화면의 3×3 합계와 크기가 다르다. A의 원값은 **비교용 지수(명/일)**로만 쓴다.
- 비교: 균등(0.025×8)은 위치 차이를 반영하지 못하고, 거리 반비례(1/d)와 가우스는 결과가 거의 같다. 가우스는 σ 하나로 "한 칸 거리에서 약 60%" 같은 설명이 쉬워서 골랐다.
- 3×3이 이미 합쳐진 `board_population`으로는 칸별 가중이 불가능해 `population_fact`를 후보 게시대의 Cell로 좁혀 읽는다(인덱스 `(cell_id, base_month)`). 가짜 데이터 290개 후보·연간 조건에서 약 0.8초.

## 4. 시뮬레이션 (가짜 데이터, `uv run python -m data_processing.simulate fake`)

| 시나리오 | 조건 |
|---|---|
| S1 카페·뷰티 오픈 홍보 | 안양 · 여성 20~30대 · **보행** · 주말 · 14~20시 · 여름 · 상업용/겸용 (59개 후보) |
| S2 자동차·보험 출퇴근 홍보 | 3개 시 · 남성 30~50대 · **주행** · 주중 · 06~10시·18~20시 · 연간 · 상업용/겸용 (290개 후보) |

**가짜 데이터의 성질을 실험에 이용했다.** 가짜 생성기는 Cell마다 성별·연령·유형 비중이 같고 규모만 다르다(비율 변동계수 3~5%, 규모 1000배 차이). 그래서 B·C에는 진짜 차이가 없고, B·C 배점이 크게 벌어지면 **노이즈를 키운다**는 뜻이다. 반대로 타깃이 결과에 반영되는지는 일부 게시대에 타깃 인구를 +50% 심어서 확인했다(E2).

| 정규화 방식 (A 지표 = N) | B 노이즈 배점 표준편차 S1 / S2 | 계절을 바꿔도 TOP 5가 다른 계절 TOP 10에 남는 비율 S1 / S2 | 타깃 +50% 심은 게시대 순위 상승 S1 / S2 |
|---|---|---|---|
| 백분위 (중간보고서 계획안) | 11.8 / 11.6점 | 0.63 / **0.18** | 13 / 85칸 |
| 최소·최대 | 6.3 / 5.0점 | 0.57 / 0.57 | 19 / 118칸 |
| **채택: A log + B·C 리프트 + 비율 보정** | **1.3 / 0.8점** | **0.97 / 1.00** | 8 / 43칸 |

- **백분위:** 0.194와 0.197처럼 거의 같은 비율도 0~40점으로 벌어져, 같은 타깃인데 계절만 바꾸면 TOP 5가 거의 다 바뀌었다(S2 겹침 0.06). 정동민 님이 우려한 "시기에 따라 값이 튀는" 현상이 산식에서 생긴다.
- **최소·최대:** 실제 신호에는 가장 민감하지만 노이즈도 키우고, 이상치 하나에 전체 척도가 끌려가 계절 간 전체 순위 상관이 0.08~0.27로 가장 낮았다.
- **채택안:** 노이즈에 강하면서 실제 타깃 신호(+50%)에도 반응한다. 비율 리프트 범위(2배=만점)는 1.25·1.5·2·3배를 비교해 안정성과 반응의 균형점으로 골랐다(E5). A를 백분위로 두면 상위권이 몰려(S2 1~5위 차이 0.5점) 계절마다 순서가 바뀌어 log 척도로 바꿨다.
- A를 N 대신 T(타깃 규모)로 바꾸는 안도 비교했다. 신호 반응은 조금 더 크지만(S2 43→63칸) 안정성이 떨어지고(1.00→0.87), log 척도에서는 이미 A+B ≈ log T라 **초안대로 N을 유지**했다.

### PRD 추천 품질 기준 점검 (E6·E7·E8)

| 기준 | 내용 | 가짜 데이터 결과 |
|---|---|---|
| N17 가중치 민감도 | 배점 ±10점 변형 4종에서 TOP 10 평균 7개 이상 유지 (대표 조건 5개) | **통과** — 평균 9.5~10.0개 유지 |
| N16 기준선 대비 | 추천 TOP 10의 타깃 인구 합 > 전체 유동 많은 순 10개 (대표 조건 10개 중 8개) | 기준선과 같음(1.000) 5개, 위 1개(1.002), 약간 아래 3개(0.987~0.997), 가장 낮은 조건 0.873 (보정 전 0.667) |

- **N16의 T는 점수와 같은 3×3 가중 합으로 잰다 (팀 결정 2026-11-21: 중심 0.8 유지).** 9칸 균등 합으로 재면 중심을 무겁게 보는 산식은 구조적으로 손해라(중심 가중치 0.3까지 낮춰도 미통과, 균등일 때만 통과) 두 결정이 서로 맞지 않는다. 균등 합 기준 비율은 리포트에 참고로 남긴다.
- 가짜 데이터는 T가 N에 비례하므로 '유동 많은 순'이 곧 '타깃 많은 순'이다. 기준선과 **같음(1.000)이 낼 수 있는 최선**이고, 기준선을 넘는지는 실제 데이터로 판단한다.
- **E8 비율 보정:** 좁은 조건(조건 8: 시흥·20대 남성·주행·7월 주말·18~20시)에서는 비율 변동계수가 35%까지 커져, 인구가 적은데 우연히 비율이 높은 게시대가 1위가 됐다(기준선 대비 0.667). 보정 세기별로 비교해 0.5를 골랐다.

  보정을 세게 할수록 튀는 결과는 줄지만 진짜 비율 차이에도 둔해진다. 가짜 데이터는 비율 차이가 노이즈뿐이라 보정이 유리하게 나오므로, 실제 데이터에서 다시 고른다(`ratio-shrink` 설정).

E9는 '전체 유동은 있는데 타깃 값이 아예 없어 계산에서 빠지는 칸'을 센다. 명세 1.1대로 NULL을 0으로 채우지 않으므로 이런 칸은 빠지고 남은 칸으로 점수를 낸다. 가짜 데이터는 가장 좁은 조건에서만 3.8%였다. 실제 데이터에서 비율이 높으면(원본에 성별·연령 조합 행이 빠진 경우) 팀과 처리 방식을 다시 정한다.

전체 표(E1~E9)는 실행하면 `data/generated_<모드>/simulation/report.md`에 생긴다. `data/` 아래라 Git에 올라가지 않으며, real 결과는 외부에 공유하지 않는다.

| `center-weight` | 0.8 | 3×3 중 소속 Cell 가중치 |
| `neighbor-sigma-meters` | 250 | 주변 칸 거리 감쇠 σ |

잘못된 값(배점 음수, `lift-span`·`size-min-span` ≤ 1, `ratio-shrink` < 0, `center-weight`가 0~1 밖 등)이면 백엔드가 시작할 때 오류를 낸다.

## 6. 추천 API(A 파트)에 넘기는 것

```java
List<ScoreFormula.Result> ranked = recommendationScorer.score(cities, purposes, populationFilter);
```

- 입력: `criteria.cities`, `criteria.purposes`, 나머지 조건은 기존 `PopulationFilter`(성별·연령·유형·시간대·기간·요일)를 그대로 쓴다. POST 본문에서 `new PopulationFilter(...)`로 직접 만들어 넘겨도 된다: `score()`가 조회 API와 같은 규칙(`PopulationFilter.from`)으로 다시 검사하므로, 빈 배열·빠진 값(계절·월)·잘못된 코드는 500이나 빈 결과가 아니라 400 `VALIDATION_ERROR`가 된다. 빠진 성별·유형·기간·요일은 조회 API와 같은 기본값(ALL·연간)을 쓴다. 지역·용도가 비었거나 잘못돼도 400 `VALIDATION_ERROR`.
- 출력: 명세 4.6 정렬이 끝난 목록. TOP 5/페이지 자르기, `rank`, `displayScore` 반올림은 API에서 한다.
- `Result.components()` = 명세 `scoreBreakdown` 재료: `key`, `label`, `rawValue`, `normalized`, `weight`(최대 배점), `points`, 그리고 B·C의 `baseline`(후보 평균 비율)·`lift`(배수).
  - 추천 이유 예: "20~30대 여성 비율이 후보 평균의 1.3배(B lift)", "보행 비중이 평균보다 높음(C lift > 1)", "유동 규모가 후보 상위권(A normalized)".
- `Result.input().matchedCellCount() < expectedCellCount()`이면 일부 칸 데이터 없이 계산된 것(PARTIAL 표시용).
- 지금 적용 중인 배점 등은 `recommendationScorer.params()`로 읽을 수 있다(응답의 `weight`와 같은 값).
- 알고리즘 버전은 `ScoreFormula.VERSION`(`provisional-v2`), 상태는 `PROVISIONAL`. `/meta`의 `algorithmVersion`(현재 `provisional-v1`)도 이 값으로 맞추면 된다.
- 추천 API가 먼저 할 검사: 데이터 미적재 → 503 `DATA_NOT_READY`, 없는 요일 구분 → 400 `UNSUPPORTED_FILTER` (조회 API와 같은 기준, `DayTypeReader`).
